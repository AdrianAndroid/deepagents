# 为什么 libs/code (dcode) 每次分析问题都要思考很久

### 轮次 1 - 分析 dcode 响应慢/思考久的原因

**用户提问要点**
- `libs/code` 下的项目（dcode 编码 agent）每次分析问题都要思考好久，为什么？

**结论/方案**
这不是 bug，而是设计特性叠加造成的，主要有四类原因：

1. **系统提示词大 + 工具多**
   - `system_prompt.md` 约 215 行 / 10KB，运行时还会动态拼接模型身份、工作目录、skills 路径、todo 指南等段落（`get_system_prompt`，`agent.py:791`）。
   - 默认注入大量中间件与工具：filesystem、shell(`execute`)、`task` 子 agent、`write_todos`、memory、skills、web_search、fetch_url 等（`create_cli_agent`，`agent.py:1306`）。
   - 每轮请求都把这一大堆 prompt + 工具定义发给模型，输入 token 多，首 token 延迟高。

2. **交互模式强制先做计划（todo）再确认**
   - 系统提示词要求：创建 todo 列表后先问用户"这个计划看起来 OK 吗？"，等确认后再开始（`agent.py:843-851`）。
   - 所以会先想、列计划、再等确认，看起来像"思考好久"。

3. **推理模型的 reasoning/thinking**
   - 若使用带 reasoning 的模型（Claude extended thinking、o 系列、或配置的 `ark-code-latest`），模型先输出隐藏思维链再回答，这段就是"思考中"。

4. **HITL 审批 + 中间件链**
   - 每个副作用工具（execute/write_file/edit_file/task 等）都被 `HumanInTheLoopMiddleware` 拦截审批（`_add_interrupt_on`，`agent.py:1198`），任务被切成多轮，每轮重新走模型。

**优化方向（待用户确认场景后细化）**
- 减少来回：`auto_approve=True`（免审批），或用 headless `-x` 模式（不强制先确认计划）。
- 降低推理开销：调低模型 reasoning effort / thinking 预算。
- 裁剪工具：关闭 `enable_skills`/`enable_memory`/`enable_shell` 等用不到的能力，缩短 prompt。

**关键操作或文件改动**
- 无代码改动；查看了 `agent.py`、`system_prompt.md`（215 行 / ~10KB）。
