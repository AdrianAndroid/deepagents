## 轮次 2 - 模型信息为何在终端看不到（remote 模式下 chunk_position 丢失）

**用户提问**：怎么打印模型信息？→ 但我没在终端看到这行信息啊。

**结论/方案**：
- 打印实现在 `libs/code/deepagents_code/textual_adapter.py`：`_format_model_call_info()` 生成一行 `· model=… finish=… tokens in/out/total=…/…/… cache_read=… elapsed=…s`，在每次模型调用最后一个 chunk（`chunk_position == "last"`）到达时作为 `AppMessage` mount。
- 用户运行 `langgraph dev` 走 remote server 模式，SSE 端下发的 AI chunk payload 里的 `chunk_position` 未被客户端透传，导致条件永远不成立，元数据行始终不显示。

**根因定位**：
`libs/code/deepagents_code/remote_client.py:_convert_ai_message()` 在重建 `AIMessageChunk` 时只读取 `content` / `tool_call_chunks` / `tool_calls` / `usage_metadata` / `response_metadata`，**未处理 `chunk_position`**。而 langchain-core v1 的 `AIMessageChunk` 会在 `model_dump()` 中带上 `chunk_position`，server 端序列化没问题；客户端漏读才是 bug。

**关键代码改动**（`libs/code/deepagents_code/remote_client.py` `_convert_ai_message`）：
```python
chunk_position = data.get("chunk_position")
kwargs: dict[str, Any] = {
    "content": content,
    "id": data.get("id"),
    "response_metadata": response_metadata,
}
if chunk_position:
    kwargs["chunk_position"] = chunk_position
```

**验证方式**：
- server 用 `--no-reload` 启动，必须重启 dcode 才能生效。
- 重启后发一句话，AI 回复末尾应出现斜体元数据行。
- 若上游 provider 没吐 `finish_reason`，langchain-core 会补一个空 last chunk，此时至少能看到 `model=… elapsed=…s`。

**知识点沉淀**：
- `chunk_position` 是 langchain-core v1 引入的 `AIMessageChunk` 属性；provider 未标注时，langchain-core 会在 stream 末尾自动补一个 `chunk_position="last"` 的空 chunk。
- 任何在 remote_client 里"用 kwargs 重建 LangChain 消息"的路径，只要 langchain 新增字段而客户端不透传，就会导致依赖该字段的 UI/统计逻辑静默失效。后续新增字段（如 `additional_kwargs`、`response_metadata` 子字段）需一并 review。

## 轮次 3 - 火山 auto 模式下如何看真实底模

**用户提问**：火山 coding plan 选的是 `auto`，但学习 deepagents 时看到 `response_metadata.model = "doubao-seed-2.0-pro"`，能拿到吗？想在终端看到真实模型请求。

**结论**：
- `auto` 只是**入参路由参数**，火山网关在响应体里会写回**实际被路由到的底模**（例如 `doubao-seed-2.0-pro`）。
- LangChain `ChatOpenAI` 会把响应体的 `model` 字段透传到 `AIMessage.response_metadata["model_name"]` / `["model"]`。
- dcode 的 `textual_adapter.py:_format_model_call_info()` 已经会在每次 AI 回复末尾打一行 `· model=…  finish=…  tokens in/out/total=…  cache_read=…  elapsed=…s`。取值优先级：`response_metadata.model_name > model > model_id`。
- 之前 remote 模式看不到这一行，就是轮次 2 修的 `chunk_position` 丢失 bug；打完补丁 + 重启就有。

**关键操作（方案 A）**：

```bash
cd libs/code
uv sync            # editable 安装当前 0.0.7 工作区
```

再重启 `langgraph dev` 和 `dcode`。之后每一 turn 都会显示实际模型，能观察到 `auto` 在不同 prompt 复杂度下会路由到不同底模。

**验证方式**：

```python
from deepagents_code.remote_client import _convert_ai_message
m = _convert_ai_message({
    "content": "hi",
    "chunk_position": "last",
    "response_metadata": {"model_name": "doubao-seed-2.0-pro"},
})
assert m.chunk_position == "last"
assert m.response_metadata["model_name"] == "doubao-seed-2.0-pro"
```

**扩展路径**（本轮未实施，备忘）：

- 方案 B：想看**完整** `response_metadata`（含 `id`、`service_tier`、`created_at`）—— 直接看 LangSmith trace（当前项目 `macmini`），或起一个 `llm.invoke("hi")` 探针脚本 print `resp.response_metadata`。
- 方案 C：想在 TUI 加更多字段，在 `_format_model_call_info()` 里补 `parts.append(f"req={id[-8:]}")` / `parts.append(f"tier={tier}")` 即可，逻辑分支保持"字段存在才追加"。

**知识点沉淀**：

- `auto` 模式下每一步的底模可能不同（火山按 prompt 动态路由），要理解"真实模型"必须逐 turn 看每条 AI message 的 `response_metadata`，不能拿第一条以偏概全。
- 如果哪次看到 `model_name == "auto"`，说明本地某个降级/未走网关的路径把入参回填了，值得排查。
- 每次调试涉及"UI 上少了一项显示"这类问题，先分层排查：**服务端有没有发 → 客户端有没有透传 → UI 有没有条件渲染**。本例是"服务端发了但客户端漏读"。

## 轮次 4 - `ark-code-latest` 为什么永远显示 `model=auto`（路由 alias vs 兼容 alias）

**用户提问**：重启后仍然显示 `model=auto`，为什么？

**根因（探针实测）**：

用 raw HTTP curl 火山 `/api/coding/v3/chat/completions`，同一 endpoint、同一协议、只换请求 `model` 名：

| 请求 `model=…`         | 响应 `model`               | alias 类型               |
|------------------------|----------------------------|--------------------------|
| `ark-code-latest`      | **`"auto"`**（故意隐藏）   | **路由 alias**（编排）   |
| `gpt-5.5`              | **`"doubao-seed-2.0-pro"`**| **兼容 alias**（固定映射）|
| `doubao-seed-2.0-pro`  | `"doubao-seed-2.0-pro"`   | 直接指定底模             |
| `gpt-4o`               | 404 `InvalidEndpointOrModel`| 不识别                   |

**关键结论**：`ark-*-latest` 是"路由 alias"，火山**故意在响应里回吐 `auto`**（产品设计而非 bug）——就是不让上游依赖具体底模。响应 headers 里也没有任何暴露底模的字段（只有 `x-request-id`）。这一层无解，只能改客户端策略。

**未来 alias 名会变**（`ark-code-latest` 可能升级为 `ark-code-v2`，`gpt-5.5` 可能替换为 `gpt-5.6`），所以不能在 config 里写死。

**探针脚本**：
- `libs/code/scripts/probe_huoshan.py` — 通过 `ChatOpenAI` 走 langchain 路径，验证 chunk 级的 `chunk_position` / `usage_metadata` / `response_metadata` 走向。
- `libs/code/scripts/probe_huoshan_responses.py` — 尝试 Responses API 路径（结论：`/api/coding/v3` 走 Responses 依然回 `auto`）。
- `libs/code/scripts/probe_huoshan_raw.py` — 裸 httpx 打 `/chat/completions`，看响应 headers/body 原始形态。
- `libs/code/scripts/probe_stream_meta.py` — 打印 LangGraph stream metadata，验证 `ls_model_name` 字段存在。

**顺便发现**：`/api/coding/v3/models` 端点是活的，返回全量真实底模列表（含 `doubao-seed-2-0-pro-260215` 等），为未来做**动态发现**留了口子。

## 轮次 5 - A 方案：UI 层区分 requested vs served model

**用户提问**：官方 alias 后续都可能变，怎么解决？→ 按 A 修改。

**方案设计（三层可选）**：
- **A. UI 层**：拿 langchain 已有的 `ls_model_name`（stream metadata），跟 `response_metadata.model_name` 对比，UI 显示 `alias→真实底模` 或 `alias(routed)`。**零代价永不过期**。
- **B. Config 层**：`models = []` 让 dcode 启动时调 `GET /models` 动态发现清单。
- **C. 启动探测层**：dcode 启动时做一次 1-token 探测，缓存 `alias → served model` 24h。

**只做 A**（10 行核心改动，落到 `libs/code/deepagents_code/textual_adapter.py`）。

**关键实现**：

1. 探针脚本 `probe_stream_meta.py` 用 `LangGraph.astream(stream_mode="messages")` 验证 stream 每个 chunk 的 metadata 里就带 `ls_model_name`（是 langchain callback 层写入的标准字段），不用改模型工厂：

```python
META: {..., 'ls_provider': 'openai', 'ls_model_name': 'ark-code-latest', ...}
```

2. `_format_model_call_info` 新增 kwarg `requested_model`。

3. 新增 `_render_model_label(requested, served)` 三态输出：
   - `served` 在哨兵集合 `{"auto"}` 内 **或** `served == requested` **且** `requested` 命中 routing marker → `f"{req}(routed)"`
   - `requested != served` 且都是真实名 → `f"{req}→{srv}"`（兼容 alias）
   - 其他 → 单个名字原样返回

4. `_looks_like_routing_alias(name)` heuristic：字符串包含 `-latest` / `-auto` / `smart-router` / `router-` / `-router`，或值等于哨兵。

5. 主循环 (`execute_task_textual`) 新增 `call_requested_model_by_namespace: dict[tuple, str]`，从每个 chunk 的 metadata 抓取 `ls_model_name`，`chunk_position=="last"` 时喂给 formatter，最后跟其它 tracker 一起 pop。

**效果对照**：

| requested | served (响应) | 之前 | 现在 |
|-----------|---------------|------|------|
| `ark-code-latest` | `auto` | `model=auto` | `model=ark-code-latest(routed)` |
| `gpt-5.5` | `doubao-seed-2.0-pro` | `model=doubao-seed-2.0-pro` | `model=gpt-5.5→doubao-seed-2.0-pro` |
| `openai:gpt-4o` | `gpt-4o` | `model=gpt-4o` | `model=gpt-4o` |
| 假如火山把 alias 改成 `ark-code-v2-latest` | `auto` | ❌ 显示错 | ✅ 自动识别为 `routed` |

**验证**：`pytest tests/unit_tests/test_textual_adapter.py -q` — 141 passed。

**知识点沉淀**：
- `ls_model_name` 是 langchain-core 通过 callback 写进 LangGraph stream metadata 的**请求 alias**，无论 gateway 怎么改写响应都不会变——这是稳定的"用户输入还原"信号。
- "网关故意隐藏底模"（如 `auto`）是**产品行为**，客户端不能试图穿透，只能在 UI 上诚实标注 `(routed)`。
- 分层解决 alias 漂移：UI 层做展示、Config 层做发现、启动层做缓存——按需组合。

## 轮次 6 - "model=ark-code-latest(routed)" 是否是硬编码

**用户提问**：一直显示这行，是写死的吗？

**结论**：**不是写死的，是真实数据组合出来的**。

| 显示片段 | 数据来源 |
|---------|---------|
| `ark-code-latest` | LangGraph stream metadata `ls_model_name`（就是 `ChatOpenAI(model=…)` 里传的字符串） |
| `(routed)` | 规则判断结论：`_looks_like_routing_alias(req)` 命中 marker **且** `served ∈ {"auto"}` 或 `served == req` |
| `finish=stop` | `response_metadata.finish_reason`（火山原样回吐） |
| `elapsed=5.1s` | 本地墙钟（第一个 chunk 到 `chunk_position=="last"`） |

**顺带遗留问题**：tokens 没显示。dcode 主循环里在 `hasattr(message, "usage_metadata")` 分支才写 `call_usage_by_namespace`，但探针数据显示 usage 只挂在**倒数第二个** chunk，last chunk 是空的。remote 模式下可能这个含 usage 的 chunk 没到达客户端（server 端有过滤 / SSE 解析漏掉）。**这个 bug 独立于本轮修改，未处理**。
